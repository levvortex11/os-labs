## Сборка и запуск в Linux/WSL

```sh
make
./merge 4
./merge 4 1000000
./merge 4 10 reverse
```

Формат: `./merge THREADS [SIZE] [random|sorted|reverse|manual]`.

- `THREADS`: положительный предел потоков от 1 до 4096, включая главный.
- `SIZE`: положительная длина до `INT_MAX`, по умолчанию 5 000 000; фактически ограничена памятью.
- Порядок данных по умолчанию `random`. Собственный 32-битный генератор начинает с 42.

### Свои числа для демонстрации

```sh
./merge 4 5 manual
```

После приглашения введите пять чисел и нажмите Enter:

```text
7 -2 10 0 7
```

Программа покажет `Before: 7 -2 10 0 7` и `After: -2 0 7 7 10`. Числа можно вводить через пробелы или на отдельных строках; завершающий Ctrl+D не нужен, когда последнее число отделено пробелом или Enter. Разрешены ноль, знаки `+`/`-` и весь диапазон `int`. Неверные токены, переполнение и EOF до получения нужного количества завершают работу с ошибкой. Читаются первые SIZE чисел.

Можно заранее вписать числа в **`examples/manual.txt`** и запустить:

```sh
./merge 4 5 manual < examples/manual.txt
```

В файле находятся только элементы, без отдельной длины. Если измените их количество, замените `5` в команде. Без `manual` данные по-прежнему генерируются автоматически. Ввод происходит до обоих измерений; обе версии получают одинаковую копию введённых чисел.

При размере до 20 выводятся массивы до и после сортировки. Затем программа выводит число элементов, лимит потоков, фактическое число созданных потоков с главным, количество логических процессоров, последовательное и параллельное время **в миллисекундах**, ускорение, эффективность и результат проверки `Check: OK`.

## Ограничение библиотек

В сдаваемой программе нет `stdio.h`, `stdlib.h`, `string.h` и вызовов `printf`, `malloc/calloc/free`, `strtol`, `strcmp`, `rand` и подобных функций. Используются POSIX `write`, `mmap`, `munmap`, `clock_gettime`, `sysconf`, `_exit` и POSIX Threads. Числа, строки и псевдослучайные данные обрабатываются собственными функциями. `errno.h`, `stdint.h` и `limits.h` нужны для определений типов, констант и обработки ошибок, а не для алгоритмов стандартной библиотеки.

POSIX-интерфейсы в Linux предоставляются системной libc; требование не означает сборку программы без libc или без стартового кода C. Флаг `-fno-builtin` исключает предположение компилятора о стандартных встроенных функциях. Исполняемый файл проверяется через `nm` на отсутствие запрещённых вызовов.

Тестовый стенд использует стандартную библиотеку и `qsort` как независимый эталон **вне основной программы**. Python применяется только для тестирования, исследования и отчёта.

## Алгоритм и лимит потоков

`merge_sort` рекурсивно сортирует половины и сливает их через `merge`. `parallel_sort` при достаточном размере отрезка создаёт один поток для левой половины, правую обрабатывает текущий. Слияние выполняется после `pthread_join`. Отдельное слияние последовательное.

`threads_left` изначально равен `THREADS - 1` и защищён мьютексом. Разрешение на создание тратится один раз и **не возвращается** после `join`: за весь запуск создаётся не больше `THREADS` потоков с главным. Это строже ограничения одновременно существующих потоков. Ожидающие родители входят в предел. Если бюджет исчерпан или участок короче 16384, используется обычная сортировка. Потоки записывают непересекающиеся участки массива и буфера. Финальное слияние снова однопоточное.

Нужно около `3 * SIZE * sizeof(int)` байт для массивов, дополнительно — память стеков. При недостатке ресурсов выводится ошибка, а не вымышленный результат эксперимента. Дерево потоков зависит от планировщика и может быть несимметричным.

## Проверка

```sh
make test
python3 tools/check_threads.py
```

45 проверок функций против независимой `qsort`, 38 проверок CLI и 15 проверок ручного ввода прошли — всего 98. Проверены границы `int`, отрицательные числа, дубликаты, длины около порога, ошибочные аргументы и большой разрешённый предел на маленьком массиве. Есть аудит библиотечных вызовов; стенд дополнительно проверен AddressSanitizer/UndefinedBehaviorSanitizer.

Скрипт `check_threads.py` наблюдает `/proc/PID/status` и показывает снимок `ps -T`. Для ручной проверки:

```sh
./merge 4 10000000 &
pid=$!
ps -T -p "$pid"
wait "$pid"
```

Первые снимки могут показывать один поток: сначала идёт последовательная версия. Сэмплирование может пропустить короткоживущий поток. Лимит, общее число созданных потоков и наблюдаемый ОС пик — разные величины.

## Эксперименты по дополнительным требованиям

На проверенной системе **12 логических процессоров**. В исследовании:

- **1, 2, 4, 8** — четыре значения меньше 12;
- **12** — равно количеству логических процессоров;
- **32, 64, 128** — три значения существенно больше 12.

```sh
python3 tools/bench.py
```

72 комбинации: три размера (10 000, 1 000 000, 5 000 000), три порядка данных и восемь пределов потоков. По три повтора — 216 успешных запусков. В `report/measurements.csv` сохранены отдельные времена в мс, медианы, число созданных потоков и наблюдаемые пики; параметры среды находятся в `report/environment.json`. Скрипт рассчитан на набор пределов для системы с 12 логическими процессорами; при другой системе набор нужно подобрать заново под условия преподавателя.

`S(P) = median(Tseq) / median(Tpar(P))`, `E(P) = S(P) / P`. Последовательная база измеряется заново для каждой строки. Время включает сортировку, создание и ожидание потоков, но не выделение памяти, генерацию, вывод, проверку и освобождение. Последовательный запуск идёт первым. Наблюдатель `/proc` создаёт небольшую дополнительную нагрузку. На 10 000 элементов дополнительные потоки не создаются из-за порога; это отдельно объяснено в отчёте.

Для 5 000 000 случайных элементов при лимитах 12, 32, 64, 128 созданы соответственно 12, 32, 64, 128 потоков с главным за весь запуск; пики одновременно существующих меньше либо равны этим числам и приведены отдельно. Графики и таблицы не выдают лимит за измеренный пик.
